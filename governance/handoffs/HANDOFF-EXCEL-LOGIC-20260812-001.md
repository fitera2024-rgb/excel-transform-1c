## 9. Ошибки и частичный результат

**ACCEPTED.** Для `Excel → validation → transformation → preview` применяется **continue with attention**, а не общий fail-closed.

### 9.1. Пользовательские состояния

- `ОК` — запись сформирована и обязательные бизнес-реквизиты разрешены.
- `Требует внимания` — запись сформирована максимально полно, но одно или несколько полей требуют явного решения/исправления.
- `Пропущено` — минимальная единица результата не может быть сформирована, остальная обработка продолжается.

### 9.2. Локализация ошибок

- **ACCEPTED.** Excel-ошибка в одной месячной ячейке не блокирует файл и не блокирует другие месяцы той же исходной строки.
- **ACCEPTED.** Соответствующая месяцу нормализованная запись не формируется/считается `Пропущено`; корректные месяцы продолжаются.
- **ACCEPTED.** Ошибка/отсутствие общего поля строки не удаляет автоматически все 12 месяцев. Корректные суммы остаются в preview, проблемное поле пустое/неразрешённое, статус `Требует внимания`.
- **ACCEPTED.** Ошибки за пределами официально обрабатываемого диапазона V1 не включаются в Реестр ошибок и не влияют на результат.
- **ACCEPTED.** Полная остановка допустима только когда полезный результат технически невозможен: файл не открывается/повреждён или не найден ни один распознаваемый диапазон.

### 9.3. Реестр ошибок

**ACCEPTED.** Для каждой проблемы сохраняется максимум доступного контекста:

- исходный файл;
- лист;
- адрес ячейки Excel;
- номер исходной строки;
- поле / месяц;
- единица отчёта;
- департамент;
- отдел / ЦФО;
- тип расходов;
- группа;
- статья;
- исходное ошибочное значение / тип Excel-ошибки;
- понятное русское описание.

Формула результата:

`Preview = все максимально сформированные данные`  
`Реестр ошибок = проблемы + точные указатели`  
`ADO-ready = только ОК, отдельный будущий контракт`

## 12. Текущий проект User Flow

10. Пользователь видит Реестр ошибок с точными ссылками на исходный Excel.
11. Пользователь исправляет бизнес-реквизиты и вручную выбирает ERP-код из утверждённых справочников.
12. Preview обновляется без потери корректных данных.

## 14. OPEN — решения, действительно требующие владельца

1. **Вид отчёта V1.** Выбрать `Отчет о прибылях и убытках` (`ОтчетОПрибыляхИУбытках`), к которому фактически относится файл показателей, либо отдельный `ОПИУ` (`ОПИУ`).
2. **Сценарий.** Разрешить расхождение `ПЛАН_2026` (подтверждённое владельцем значение текущего примера) и `ПЛАН 2026`/`00010` в актуальном экспорте; определить однозначный persisted key при неуникальных кодах.
3. **Периоды.** Определить ключ выбора и допустимый состав экранного списка, поскольку ERP-код пуст, есть произвольные периоды и аномальные годы.
4. **Организационный контекст ПС.** Утвердить mapping `единица отчёта ПС ↔ юридическая организация/ветка ↔ ПС/Б_ПС ЦФО`; единица и организация остаются разными реквизитами.
5. **Статус и тип узла Organizations.** Предоставить/утвердить источник признаков `Действует`, `ЦФО`, юридическая организация, так как screenshot их показывает, а текущий Excel-export не даёт надёжного usable поля.
6. **Цель делегации.** Разрешена ли делегация только на узлы-организации или также на отдельное подразделение/ЦФО.
7. **Reusable manual mapping context.** Утвердить точный состав context key, в котором можно повторно применять подтверждённый ERP-код/override.
8. **Отрицательные суммы.** Подтвердить, допустимы ли они без отдельного подтверждения и какие статьи/контексты являются исключениями.
9. **User Flow acceptance.** После закрытия действительно необходимых пунктов владелец должен явно принять User Flow; до этого implementation не начинается.

Недостающие данные, которые пока не являются принятым решением:

- отдельный актуальный справочник единиц отчёта;
- утверждённый справочник налогообложения;
- явная версия/признак актуальности справочников;
- правила хранения/обновления справочников и overrides — проектируются после принятия User Flow, без преждевременной архитектуры.
