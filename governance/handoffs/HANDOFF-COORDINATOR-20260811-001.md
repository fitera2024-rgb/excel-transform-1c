## 1. Что это за сервис

Лёгкий внутренний сервис для цепочки:

`Excel → validation → transformation → preview → later ADO DRY RUN → controlled 1C write`.

Ключевая продуктовая установка владельца: **это быстрый рабочий помощник, а не тяжёлый контрольный шлюз**. Нельзя переносить в него многоходовые блокировки OPIU. Приоритет — обработать максимум корректных данных, показать полный preview и отдельно дать понятный реестр проблем.

OPIU используется только как visual/UX reference и источник отдельных проверенных reliability/safety patterns. Новый сервис не является fork OPIU и не должен наследовать R005, R001, Rules Engine, source-proof UI, evidence/SHA controls и тяжёлый release/governance UX без отдельной необходимости.

## 4. Дополнительные ЯВНО ПРИНЯТЫЕ решения владельца, которые координатор должен считать текущим Product Contract

### 4.1. Источник первой версии

Официальный вход первой версии — **уже подготовленный загрузочный диапазон Excel**.

Сервис НЕ реконструирует загрузочные строки из восьми расчётных листов департаментов, `полный массив`, исторических листов и внутренних формул бюджета.

Лист определяется **по структуре обязательных колонок и данным**, а не по точному имени. В реальных примерах встречались варианты `загрузка в ERP расходы` и `загрузка ERP расходы`.

### 4.2. Нулевые месяцы

Для каждой исходной загрузочной строки формируются все 12 месяцев, включая нулевые значения. Нули не отбрасываются только ради компактности результата.

Для текущего исследованного примера: `179 исходных строк × 12 = 2148 нормализованных строк`.

### 4.3. ERP-сопоставление статей

При точном однозначном совпадении по полной иерархии можно использовать найденный ERP-код.

Если точного однозначного соответствия нет, пользователь может вручную выбрать ERP-код.

Запрещено автономное fuzzy-сопоставление, автоматическое исправление опечаток или выбор кода только по имени статьи.

В текущем UX это **не должно блокировать весь файл**: запись остаётся в preview как `Требует внимания`, проблема попадает в Реестр ошибок/внимания. Строгий ADO-ready фильтр проектируется позже отдельно.

### 4.4. Выход первой версии

Не копировать технический 34-колоночный формат исследованного sample-result.

Пользовательский нормализованный результат OPIU Light должен как минимум содержать бизнес-поля:

- единица отчёта;
- сценарий;
- год / месяц / период;
- департамент;
- вид организации;
- отдел / ЦФО;
- тип расходов;
- группа расходов;
- исходное название статьи;
- ERP-код статьи;
- официальное название ERP-статьи;
- налогообложение;
- сумма;
- статус сопоставления/готовности;
- комментарий / причина внимания;
- номер исходной строки.

Технические SHA, BatchID, internal keys, paths, технические blocker codes и подобные поля не являются обязательными пользовательскими колонками. При необходимости они остаются во внутреннем RUN/manifest/support layer.

### 4.5. Контекст задаёт пользователь в сервисе из загруженных справочников

В первой версии контекст не должен жёстко зашиваться и не должен угадываться по имени файла/пути/случайной ячейке Excel.

Владелец загружает реальные справочники; пользователь выбирает значения в UI.

Нужны/ожидаются справочники как минимум для:

- единиц отчёта;
- организаций пути 1С;
- сценариев;
- периодов сценария;
- видов отчётов;
- ЦФО / подразделений;
- налогообложения, если есть отдельный справочник;
- прочих связанных справочников, если они реально нужны процессу.

После выбора сервис может сверять Excel с выбранным контекстом. Явное противоречие нужно показать пользователю, но не создавать тяжёлую многоходовую блокировку без необходимости.

### 4.6. Не объединять `Единицу отчёта` и `Организацию пути 1С`

Это разные бизнес/интеграционные реквизиты.

Исследованный бюджетный Excel содержал единицу отчёта `ПС` (а в другом примере `АЮ`).

В реальном интерфейсе 1С для пути была показана организация `Владивосток`.

Нельзя автоматически делать вывод `ПС → Владивосток` или аналогичное соответствие без отдельного справочника/правила.

Также не объединять `Сценарий` и `Период сценария`: 1С показывает их как отдельные элементы пути. Исследованный сценарий: `ПЛАН_2026`, но это пример, а не hardcode.

### 4.7. Формулы Excel разрешены

Пользователь **не обязан** делать Copy → Paste Values.

В исходном загрузочном диапазоне могут оставаться формулы. Первая версия сервиса:

- использует рассчитанное/сохранённое значение ячейки;
- не анализирует бизнес-смысл формулы;
- не воспроизводит Excel Calculation Engine;
- не должна требовать преобразования формул в значения.

Если отдельная ячейка даёт Excel-ошибку (`#REF!`, `#N/A`, `#DIV/0!` и т.п.), это **не блокировка всего файла**. Нельзя перенести только минимально необходимое значение/объект; остальная обработка продолжается. Проблема попадает в Реестр ошибок с точным указателем на источник.

Ошибки за пределами официально обрабатываемого загрузочного диапазона не должны блокировать первую версию.

### 4.8. Налогообложение

Из исследованного файла реально встречались:

- `БЕЗ НДС`;
- `0.2`;
- `0.22`;
- `?`;
- числовой `0`;
- пустые исходные значения, часть которых могла превращаться в `0`.

`0.2` можно детерминированно интерпретировать как `20%`, `0.22` как `22%`.

Критически важно: числовой `0` нельзя автоматически считать ставкой `0%`, потому что в текущем Excel он также мог происходить из пустого источника.

После принятия Light error handling значения `?`, пусто, неоднозначный `0` и другие проблемы **не останавливают файл**: запись остаётся в preview максимально полной и получает `Требует внимания`; пользователь может исправить реквизит в сервисе, когда будут загружены соответствующие справочники.

### 4.9. Пользователь может исправлять бизнес-реквизиты прямо в сервисе

Явное решение владельца: **ДА**.

Допускается исправлять в UI не только ERP-код статьи, но и ошибочные/неполные бизнес-реквизиты, например:

- налогообложение;
- департамент;
- ЦФО;
- группу;
- статью;
- другие поля, для которых существует утверждённый загруженный справочник.

Исправление должно быть пользовательским override, а не тихой автоматической подменой источника. Желательно сохранять исходное значение и выбранное пользователем значение во внутреннем trace/audit, но не превращать UX в технический proof-screen.

### 4.10. Базовый UX ошибок

Основные пользовательские состояния первой версии:

- `ОК`;
- `Требует внимания`;
- `Пропущено`.

Правило: **не удалять полезные данные из preview из-за локальной проблемы**.

`Preview = максимально полный результат`

`Реестр ошибок = проблемы + точные указатели`

`ADO-ready = отдельный будущий фильтр`

Полная остановка обработки оправдана только если технически невозможно продолжить вообще: например, файл не открывается/повреждён или не найден ни один распознаваемый загрузочный диапазон.

## 5. Реестр ошибок / внимания — принятая концепция

Для каждой локальной проблемы пользователь должен быстро понять, где она находится в Excel. Ожидаемые указатели:

- исходный файл;
- лист;
- адрес ячейки (например `N43`) если проблема ячеечная;
- номер исходной строки;
- поле/месяц;
- единица отчёта;
- департамент;
- отдел/ЦФО;
- тип расходов;
- группа;
- статья;
- исходное проблемное значение / тип Excel-ошибки;
- понятное русское описание.

Не требуется, чтобы каждая проблема имела все поля — сохраняется максимум доступного контекста.

Отмечен подозрительный `0 Отдел логистики` на двух строках — это пример значения, которое нужно показывать как требующее внимания, а не останавливать весь файл.

## 8. Факты из реального 1С-интерфейса/скриншотов

В `Внешние информационные базы` исследован ADO/Excel source для бюджета. Path-конфигурация 1С содержит элементы:

1. `Период сценария`;
2. `Сценарий`;
3. `Организация`;
4. `Вид отчета`.

Отдельная форма `Элементы пути к файлам организаций` содержит tabs:

- Периоды;
- Сценарии;
- Организации;
- Проекты;
- Виды отчетов.

`Проект` существует в общем механизме 1С, но в наблюдаемом пути текущего импорта его не было. Поэтому не делать его обязательным контекстом первой версии без нового доказательства/решения.

На вкладке сценариев наблюдалось значение `ПЛАН_2026`.

На вкладке организаций наблюдалось значение `Владивосток`.

Это подтверждает разделение бюджетной `Единицы отчёта` (`ПС`/`АЮ`...) и `Организации пути 1С` (`Владивосток` в наблюдаемом примере).

ADO/network path — будущая интеграционная граница. Он не должен становиться текущим источником истины для Excel → transform → preview и не даёт разрешения на write.

## 10. Предпочтительный User Flow первой версии

Детали ещё DRAFT, но текущая принятая логика продукта требует примерно такой путь:

1. Пользователь загружает/обновляет необходимые справочники либо сервис использует уже загруженные утверждённые справочники.
2. Пользователь выбирает контекст в UI: `Период сценария → Сценарий → Единица отчёта → Организация пути 1С → Вид отчёта` (точные зависимости уточнить по реальным справочникам; не hardcode).
3. Выбирает бюджетный Excel.
4. Сервис структурно находит подготовленный загрузочный диапазон.
5. Читает рассчитанные значения, валидирует и нормализует 12 месяцев.
6. Выполняет точное ERP-сопоставление по иерархии там, где это однозначно.
7. Показывает основной максимально полный preview.
8. Показывает Реестр ошибок/внимания с точными указателями.
9. Пользователь может прямо в UI исправлять бизнес-реквизиты из загруженных справочников и выбирать ERP-код.
10. Preview обновляется без необходимости многократно чинить Excel для каждой локальной ошибки.

Строгие требования ADO-ready/write определяются отдельным последующим этапом и не должны утяжелять первую vertical slice.

## 11. Architecture Light / safety boundary

Целевая архитектура:

`UI → Application/Workflow → Business Core → Adapters (Excel / References / later ADO) → Audit/Runs/Support`.

Business Core не должен знать про UI buttons, ADO connection objects и абсолютные filesystem paths.

Надёжные patterns, которые разрешено взять из OPIU без тяжёлого UX:

- structural source detection, не filename authority;
- immutable run-local input snapshot;
- single-flight/idempotent business action;
- business-safe DTO allowlist;
- reselect/reset без side effects;
- exact handoff downstream, не `latest file`;
- release freshness gate;
- clean-room package launch;
- support bundle без секретов.

Но первая vertical slice — **без ADO live write**.

Если в будущем ADO означает прямой SQL-write во внутренние таблицы 1С, это отдельное high-risk архитектурное решение. Предпочтительнее контролируемый receiver/staging, если это возможно в реальном контуре.

- точная семантика `Периода сценария` относительно года нормализованного результата;

- отдельное правило отрицательных сумм;
- какие ошибки/неполноты должны влиять на будущий ADO-ready статус;
- нужен ли `Проект` в каком-либо реальном сценарии.
