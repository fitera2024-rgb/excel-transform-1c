# Decisions

Принятые решения не переписываются молча. Изменение принятого решения фиксируется новой записью с указанием supersedes/refines.

## DEC-BOOT-001 — Project boundary

STATUS: `ACCEPTED`

- Новый сервис создаётся отдельным репозиторием, не fork/branch OPIU.
- OPIU используется только как visual/UX reference и источник проверенных reliability/safety patterns.
- R005, R001, Rules Engine и source-proof UI не входят в новый сервис по умолчанию.

## DEC-BOOT-002 — Delivery order

STATUS: `ACCEPTED`

- Сначала Product Contract и User Flow.
- Первая vertical slice: Excel → validation → transformation → preview.
- ADO/write проектируется позже отдельным high-risk этапом.
- Production live-write только после отдельного owner gate.

## DEC-PRODUCT-001 — Light error handling

STATUS: `ACCEPTED`

- Новый сервис — быстрый рабочий помощник, а не контрольный шлюз.
- Основной принцип первой версии: обработать максимум корректных данных и собрать проблемы в понятный Реестр ошибок.
- Локальная ошибка не блокирует обработку всего файла; пропускается только минимально необходимая проблемная единица данных.
- Пользовательские состояния: `ОК`, `Требует внимания`, `Пропущено`.
- Частичный полезный результат разрешён.
- Полная остановка допускается только когда технически невозможно продолжать обработку вообще.
- Более строгие ограничения для ADO/live-write определяются отдельно и не переносятся автоматически на Excel → validation → transformation → preview.

## DEC-PRODUCT-002 — Minimum-loss transfer on shared-field errors

STATUS: `ACCEPTED`

Refines: `DEC-PRODUCT-001`.

- Ошибка в общем поле исходной строки (`статья`, `группа`, `департамент`, `ЦФО`, `налогообложение` и т. п.) не исключает автоматически все 12 месяцев этой строки.
- Сервис переносит все данные, которые можно сформировать корректно.
- Не переносится только минимальная часть результата, которую действительно невозможно сформировать из-за конкретной ошибки.
- Корректные месяцы и корректные поля сохраняются; проблемное поле фиксируется как требующее внимания и попадает в Реестр ошибок с точным указателем на источник.
- Если без проблемного поля конкретный выходной объект всё же можно сформировать, он не должен удаляться только из-за неполноты другого поля.
- Правило `ошибка общего поля → исключить всю исходную строку/12 месяцев` запрещено для первой версии.

## DEC-PRODUCT-003 — Keep incomplete records visible in preview

STATUS: `ACCEPTED`

Refines: `DEC-PRODUCT-001`, `DEC-PRODUCT-002`.

- Основной нормализованный preview/result показывает максимально полный результат, включая записи с корректными суммами и локально неразрешёнными общими реквизитами.
- Такие записи остаются в основном preview/result со статусом `Требует внимания`.
- Проблемное поле может оставаться незаполненным/неразрешённым, а проблема одновременно фиксируется в Реестре ошибок с точным указателем на источник.
- Не создавать отдельный скрытый карантин для неполных записей первой версии.
- Локальная проблема не должна визуально удалять корректную сумму из preview.
- Готовность к фактической ADO-загрузке определяется отдельным будущим ADO-ready контрактом и не ограничивает полноту текущего preview.

## DEC-PRODUCT-004 — Prepared load range is V1 source

STATUS: `ACCEPTED`

- Официальный вход первой версии — уже подготовленный загрузочный диапазон Excel.
- Сервис не реконструирует загрузочные строки из расчётных листов департаментов, hidden full-array, historical sheets и внутренних формул бюджета.
- Загрузочный диапазон распознаётся структурно по обязательным колонкам/данным, а не по точному имени листа.
- Варианты имени вроде `загрузка в ERP расходы` и `загрузка ERP расходы` не должны требовать отдельного hardcode.

## DEC-PRODUCT-005 — Preserve all 12 months including zero

STATUS: `ACCEPTED`

- Каждая исходная загрузочная строка нормализуется во все 12 месяцев.
- Нулевые месяцы сохраняются и не удаляются как «лишние».
- Для исследованного набора 179 строк ожидаемое количество нормализованных записей — 2148.

## DEC-PRODUCT-006 — ERP mapping by hierarchy with manual fallback

STATUS: `ACCEPTED`

- Имя статьи само по себе не является глобальным ключом.
- Автоматический ERP-код допускается только при точном однозначном сопоставлении по принятой иерархии/атрибутам.
- При отсутствии точного однозначного match пользователь выбирает ERP-код вручную.
- Запрещены автономный fuzzy auto-match, автоматическое исправление опечаток и самостоятельный выбор кода сервисом при неоднозначности.
- Неразрешённый mapping не блокирует весь preview: запись остаётся `Требует внимания`; будущий ADO-ready определяется отдельно.

## DEC-PRODUCT-007 — User-selected context from loaded references

STATUS: `ACCEPTED`

- Контекст первой версии задаётся пользователем в интерфейсе из загруженных утверждённых справочников.
- Значения не hardcode-ятся и не определяются по имени файла, path или случайной ячейке workbook.
- Ожидаются справочники единиц отчёта, организаций пути 1С, сценариев, периодов сценария, видов отчётов, ЦФО/подразделений, налогообложения и других реально необходимых связей.
- `Единица отчёта` и `Организация пути 1С` — разные поля до доказанного mapping.
- `Сценарий` и `Период сценария` — разные поля.
- Наблюдаемые значения `ПС`, `АЮ`, `Владивосток`, `ПЛАН_2026` являются примерами, а не hardcode.
- `Проект` существует в общем механизме 1С, но не становится обязательным полем первой версии без отдельного доказательства/решения.

## DEC-PRODUCT-008 — Formula results are accepted; errors are localized

STATUS: `ACCEPTED`

- Пользователь не обязан преобразовывать формулы в значения перед обработкой.
- В загрузочном диапазоне формулы разрешены; сервис читает рассчитанные/сохранённые значения.
- Сервис первой версии не является Excel Calculation Engine и не воспроизводит бизнес-логику формул.
- Ошибка отдельной ячейки (`#REF!`, `#N/A`, `#DIV/0!` и т. п.) не блокирует весь файл; пропускается только минимально необходимая часть, проблема регистрируется с точным указателем.
- Ошибки вне официально обрабатываемого загрузочного диапазона не блокируют первую версию.

## DEC-PRODUCT-009 — Business attributes may be corrected in service UI

STATUS: `ACCEPTED`

- Пользователь может исправлять в интерфейсе сервиса не только ERP-код, но и бизнес-реквизиты: налогообложение, департамент, ЦФО, группу, статью и другие поля, если для них есть утверждённый загруженный справочник.
- Пользовательская правка является явным override, а не тихой автоматической подменой источника.
- Исходное и выбранное значения допускается сохранять во внутреннем trace/audit без технического proof-UX в normal UI.
- Не требовать исправлять каждую локальную проблему только через редактирование исходного Excel и повторную обработку.

## DEC-PRODUCT-010 — Tax value ambiguity is attention, not whole-file blocker

STATUS: `ACCEPTED`

Refines: `DEC-PRODUCT-001`, `DEC-PRODUCT-009`.

- В исследованном наборе `БЕЗ НДС`, `0.2`, `0.22` являются распознаваемыми значениями; `0.2` нормализуется как 20%, `0.22` как 22%.
- `?`, пустое и неоднозначный числовой `0` требуют внимания.
- Числовой `0` нельзя автоматически трактовать как 0%, потому что в исследованном Excel он мог происходить из пустого источника.
- Эти проблемы не блокируют весь файл: запись остаётся максимально полной в preview со статусом `Требует внимания` и может быть исправлена пользователем из утверждённого справочника.

## DEC-PRODUCT-011 — Local budget converter and proportional safeguards

STATUS: `ACCEPTED`

Refines: `DEC-BOOT-001`, `DEC-BOOT-002`, `DEC-PRODUCT-001`.

- Практическая цель продукта — локально и повторяемо преобразовывать ограниченный набор типов бюджетных Excel-таблиц в согласованный формат для 1С.
- Продукт не проектируется как универсальная интеграционная платформа, multi-tenant SaaS, глобальный сервис или framework для произвольных Excel/ERP-сценариев.
- Первая и главная ценность — корректная трансформация, понятный preview, исправление бизнес-реквизитов и получение результата, пригодного для дальнейшей загрузки в 1С.
- Архитектура, тесты, логирование, авторизация, packaging и governance должны быть соразмерны локальному применению и фактическому риску.
- Запрещено циклически добавлять safety/governance-контроли без конкретного реалистичного сценария отказа, проверяемой пользы и отсутствия более простого решения.
- Для этапа `Excel → validation → transformation → preview` минимально достаточны: детерминированная трансформация, понятная локализация ошибок, отсутствие тихой потери корректных данных, повторяемость и точная связь результата с выбранным входом.
- Multi-tenant архитектура, enterprise RBAC, универсальные Rules/Plugin Engine, cryptographic proof UI, тяжёлый audit, распределённая инфраструктура и сложное release orchestration не входят в scope без отдельного доказанного требования владельца.
- Усиленные safety-меры применяются только там, где появляется фактическая запись в 1С/БД, риск дубля, неверная цель записи или необратимое изменение; и там выбирается самое простое достаточное решение.
- Это решение не разрешает live write и не отменяет отдельный owner gate для фактической записи в 1С/БД.

## DEC-PRODUCT-012 — Continue preview instead of generalized fail-closed

STATUS: `ACCEPTED`

Refines: `DEC-PRODUCT-001`, `DEC-PRODUCT-002`, `DEC-PRODUCT-003`, `DEC-PRODUCT-006`, `DEC-PRODUCT-011`.

- Для этапа `Excel → validation → transformation → preview` выбран принцип продолжения обработки с локализацией проблемы, а не общий fail-closed всего процесса.
- Неоднозначный или отсутствующий бизнес-реквизит, контекстное значение, ERP-сопоставление либо отдельное поле будущего target не блокируют весь preview, если сервис может прочитать распознаваемый загрузочный диапазон и сформировать полезную часть результата.
- Сервис не должен молча угадывать неоднозначное значение. Оно остаётся неразрешённым, запись получает `Требует внимания`; только минимально неформируемая единица получает `Пропущено`; остальные данные продолжают обрабатываться.
- Когда проблему можно разрешить пользовательским выбором, интерфейс предлагает понятное действие выбора или исправления без необходимости заново запускать весь процесс.
- Полная остановка первой vertical slice допускается только при технической невозможности получить какой-либо полезный результат: файл не открывается/повреждён либо не найден ни один распознаваемый загрузочный диапазон.
- Обобщённое правило `неоднозначность source/context/target → остановить весь этап` для preview не применяется.
- Для будущей фактической записи в 1С неоднозначность реального места назначения может блокировать только write-операцию; уже сформированные validation, transformation и preview сохраняются. Разрешение live write по-прежнему требует отдельного owner gate.

## DEC-PRODUCT-013 — Organizations, subdivisions and CFOs form one nested directory

STATUS: `ACCEPTED`

Supersedes: предположение о двух независимых справочниках `Организации` и `ЦФО`.

- Юридические организации, промежуточные организационные узлы, подразделения и ЦФО рассматриваются как узлы одного вложенного справочника `Организации`.
- Экранные списки не должны создавать независимые несвязанные значения organization/CFO.
- Выбранный подразделенческий узел должен принадлежать выбранной/разрешённой ветке дерева.
- `Единица отчёта` остаётся отдельным бизнес-реквизитом и не объединяется с узлом справочника без доказанного mapping.

## DEC-ACCESS-001 — Delegation grants the whole organization subtree

STATUS: `ACCEPTED`

- Делегация на организацию распространяется на сам узел и всё его поддерево любой глубины.
- Доступ наследуется через любые промежуточные уровни до всех подразделений и ЦФО.
- Соседние и вышестоящие ветки автоматически не открываются.
- Экранные списки организационного контекста фильтруются этой разрешённой веткой.

## DEC-ACCESS-002 — Multiple delegations are combined

STATUS: `ACCEPTED`

Refines: `DEC-ACCESS-001`.

- Одному пользователю может быть делегировано несколько организаций.
- Effective access является объединением всех соответствующих поддеревьев.
- Пересекающиеся узлы не дублируются.
- Это минимально достаточная иерархическая модель доступа локального сервиса, а не основание для построения enterprise RBAC framework.

## DEC-PRODUCT-014 — Manual mapping reuse requires proven same context

STATUS: `ACCEPTED`

Refines: `DEC-PRODUCT-006`, `DEC-PRODUCT-009`.

- Явно подтверждённое пользователем соответствие ERP-коду может повторно применяться только в доказанно том же business context.
- Одно исходное название статьи не может быть reusable global key.
- При конфликте иерархии сервис не игнорирует её самостоятельно; требуется явный пользовательский выбор.
- Точный состав persisted context key остаётся отдельным OPEN Product Contract решением.

## DEC-PRODUCT-015 — V1 report type is Profit and Loss

STATUS: `ACCEPTED`

Refines: `DEC-PRODUCT-007`.

- В первой версии поддерживается вид отчёта `Отчет о прибылях и убытках` с кодом `ОтчетОПрибыляхИУбытках`.
- Фактический экспорт показателей из 682 записей был сформирован с фильтром именно по этому виду отчёта, поэтому решение соответствует исследованным данным.
- Отдельная запись справочника `ОПИУ` с кодом `ОПИУ` не используется как вид отчёта V1.
- В интерфейсе V1 выбранный вид отчёта показывается как фиксированный контекст либо единственная доступная опция; пользователь не должен выбирать между двумя близкими значениями.
- Поддержка дополнительных видов отчётов требует отдельного owner decision.

## DEC-PRODUCT-016 — Scenario identity and local scenario creation

STATUS: `ACCEPTED`

Refines: `DEC-PRODUCT-007`.

- `ПЛАН_2026` и `ПЛАН 2026` считаются одним сценарием.
- Каноническое наименование: `ПЛАН 2026`; год: `2026`.
- ERP-код `00010` хранится как дополнительный атрибут и не является единственным ключом.
- Основной persisted identity — стабильный локальный идентификатор сценария.
- Пользователь может добавить новый сценарий с наименованием, годом и необязательным комментарием.
- Новый сценарий постоянно сохраняется локально, доступен в следующих запусках и виден всем пользователям локального сервиса.
- Сценарий без ERP-подтверждения разрешён для validation, transformation, preview и экспорта и помечается `Не подтверждён справочником ERP`.
- Пользователь может позднее создать или поправить сценарий в ERP; до подтверждения будущий write запрещён.

## DEC-PRODUCT-017 — Period selection uses year and optional months

STATUS: `ACCEPTED`

Refines: `DEC-PRODUCT-005`, `DEC-PRODUCT-007`.

- Интерфейс содержит отдельные элементы выбора года и месяца.
- Допустимы: только год; год и один/несколько месяцев; только месяц(ы), если год однозначно задан сценарием.
- Внутренняя identity месячной записи — календарный год и номер месяца `1–12`.
- Трансформация всегда формирует все 12 месяцев, включая нулевые; месячный выбор является фильтром просмотра/экспорта и не разрушает полный результат.

## DEC-PRODUCT-018 — Organization branch is selected manually per run

STATUS: `ACCEPTED`

Refines: `DEC-PRODUCT-007`, `DEC-PRODUCT-013`.

- Для единицы отчёта `ПС` заранее не устанавливается mapping на юридическую организацию, ветку `ПС` или `Б_ПС`.
- Пользователь выбирает нужный узел/ветку вручную при каждом запуске.
- Все узлы загруженного дерева показываются без автоматического фильтра по не доказанным полям `Статус` и `Тип узла`.
- Для различения показываются доступные код и полный путь.
- Названия `!!!Удалить` и `Удалить` не являются основанием для автоматического скрытия или исключения.

## DEC-ACCESS-003 — Delegation may target any tree node

STATUS: `ACCEPTED`

Refines: `DEC-ACCESS-001`, `DEC-ACCESS-002`.

- Делегация может быть выдана на любой узел дерева: организацию, подразделение, ЦФО или промежуточный узел.
- Доступ включает выбранный узел и всё его поддерево любой глубины.
- Модель остаётся простой локальной иерархической фильтрацией.

## DEC-PRODUCT-019 — Reusable ERP mapping key

STATUS: `ACCEPTED`

Refines: `DEC-PRODUCT-014`.

- Ручной ERP mapping повторно применяется при совпадении вида отчёта и полного пути `тип расходов → группа расходов → исходная статья`.
- Организация, департамент и ЦФО не входят в базовый reusable key.
- При обнаружении реального конфликта mapping не применяется молча и снова требует пользовательского выбора.

## DEC-PRODUCT-020 — Negative amounts remain visible with attention

STATUS: `ACCEPTED`

Refines: `DEC-PRODUCT-001`, `DEC-PRODUCT-003`.

- Отрицательная сумма сохраняется без изменения знака и не пропускается.
- Запись остаётся в основном preview/result.
- Статус: `Требует внимания`.
- Комментарий: `Отрицательная сумма`.
- Сервис не решает самостоятельно, является ли отрицательное значение ошибкой или допустимым резервом.

## DEC-PRODUCT-021 — V1 User Flow accepted

STATUS: `ACCEPTED`

Refines: `DEC-BOOT-002`.

- Владелец явно принял `docs/USER_FLOW.md` для первой vertical slice.
- Разрешена подготовка и последующее исполнение implementation task для `Excel → validation → ERP mapping → user corrections → 12-month normalization → preview → export`.
- Для начала реализации V1 не осталось Product Contract вопросов, требующих владельца.
- ADO/live write и запись в 1С/БД по-прежнему запрещены до отдельного owner gate.

## DEC-UX-012 — Explicit tax-not-required decision

STATUS: `ACCEPTED`

- Для причины `Налогообложение не определено` пользователь может явно выбрать `Налогообложение неважно`.
- Результат хранится как бизнес-значение `Не требуется`; налоговый режим автоматически не определяется.
- Решение снимает только tax-причину, применяется ко всем месяцам source row без rerun и не скрывает другие проблемы.
- Отдельное массовое действие требует явной галки, считает source rows и является идемпотентным.

## DEC-REF-003 — Exact Intalev CFO to 1C node mapping

STATUS: `ACCEPTED`

- Классификатор ЦФО Инталев загружается структурно и сохраняется локально.
- Каждый exact source CFO сопоставляется с конкретным узлом загруженного дерева 1С.
- Выбор организации RUN и mapping source CFO — разные реквизиты.
- Fuzzy/name-only/typo/case-insensitive guessing запрещён; неоднозначность закрывает только конкретный mapping.
- Подтверждённое соответствие повторно используется после restart и в следующих RUN.
- Массовое действие считает уникальные source CFO и применяет набор атомарно после server-side revalidation.

## DEC-UX-013 — Separate explicit bulk actions and confirmed statuses

STATUS: `ACCEPTED`

- ERP, налог и ЦФО имеют отдельные галки, счётчики и кнопки; одна галка не подтверждает три разных решения.
- Master checkbox ничего не меняет до submit.
- После подтверждения UI показывает бизнес-статус (`ERP-сопоставление подтверждено`, `Налогообложение: не требуется`, `Сопоставление ЦФО подтверждено`) и не предлагает тот же элемент повторно.

## DEC-REF-004 — Packaged baselines remain and user imports supplement them

STATUS: `ACCEPTED`

Refines: `DEC-REF-003`, `DEC-PRODUCT-016`.

- Чистый пакет автоматически содержит проверенные базовые каталоги ERP-статей, организаций/узлов, сценариев и ЦФО Инталев.
- `Загрузить / дополнить` не удаляет baseline: новые записи добавляются, exact-key записи могут быть обновлены, похожие display names не объединяются.
- При обновлении пакета недостающие baseline-записи восстанавливаются, но пользовательское значение того же exact key остаётся authoritative.
- Каталоги и mappings сохраняются в локальной SQLite после restart.

## DEC-INPUT-006 — Content-based Excel preparation and native Intalev OPIU

STATUS: `ACCEPTED`

Refines: `DEC-PRODUCT-001`, `DEC-PRODUCT-021`.

- Формат определяется по bytes/internal structure, не по filename suffix.
- V1 принимает обычный OOXML, защищённый OOXML, legacy BIFF/XLS, SpreadsheetML XML и узко восстанавливаемый OOXML.
- Original RUN-local snapshot неизменяем; decrypt/convert/repair выполняется только в отдельной working copy.
- Помимо подготовленного бюджетного диапазона принят годовой Инталев ОПИУ с отдельным structural parser и OPIU Light export.
- Невосстанавливаемая или неоднозначная техническая структура fail closed; Excel COM и ручной SaveAs не являются пользовательским требованием.

## DEC-UX-014 — FITERA visual shell

STATUS: `ACCEPTED`

- `FITERA_SERVICE_UI_STARTER_V2` используется как visual/UX reference, без переноса чужой backend-логики.
- Сохраняются business forms, input names, endpoints, test hooks и отдельные explicit actions ERP/tax/CFO.
- Normal UI использует фирменную бело-зелёную оболочку, понятные шаги и бизнес-статусы; SHA, paths и technical blocker codes не становятся обязательными полями.
