## Цель

Убрать необходимость ручной работы с техническими правилами. Сервис должен сам находить прямое уникальное соответствие между статьёй результата и показателем из загруженного классификатора, формировать лист `Показатели` и показывать пользователю только остаток, требующий решения.

## Business contract

1. Сохранить экспорт из трёх листов:
   - `OPIU Light` — прежняя схема без регрессии;
   - `ОПИУ` — ADO-схема;
   - `Показатели` — автоматически заполненная ADO-схема.
2. Классификатор соответствий загружается как локальный справочник и может дополняться.
3. Прямое соответствие применяется автоматически только при одном точном кандидате.
4. При `0` или `>1` кандидатах — fail closed и `Требует внимания`.
5. Запрещены fuzzy, typo, case-only и contains matching.
6. Нельзя выдумывать показатель, канал сбыта или справочный код.
7. Отсутствующие справочные коды остаются пустыми и не удаляют строку.

## Exact matching

Поддержать прямые правила с доказанными полями классификатора. Приоритет ключей:

1. точный ERP-код статьи;
2. точный полный путь статьи;
3. точное имя статьи только при уникальности в классификаторе.

Нормализация допускается только техническая и обратимая: trim пробелов и сохранение исходного значения. Не менять регистр и не исправлять текст.

## Indicator output

Лист `Показатели` содержит колонки:

1. Организация;
2. Сценарий;
3. Год;
4. Месяц;
5. Период;
6. Канал сбыта;
7. Тип расходов;
8. Сумма.

Правила формирования:

- строки создаются только для уникально сопоставленных правил;
- `Тип расходов` получает точное значение показателя из классификатора;
- `Канал сбыта` получает точное значение из классификатора либо доказанного поля источника;
- одинаковый выходной ключ агрегируется суммой;
- нули и отрицательные значения сохраняются;
- месячная ошибка не превращается в число;
- отсутствие/неоднозначность остаётся проблемой preview.

## Simplified UI

Normal user не должен редактировать технические Rules.

На preview показать компактный блок:

- `Найдено автоматически: N`;
- `Требует внимания: N`;
- `Не найдено: N`;
- `Классификатор соответствий: загружен / не загружен`;
- действие `Загрузить / дополнить классификатор`;
- ручной выбор только для нерешённых строк.

После дополнения классификатора текущий RUN должен уметь повторно применить автопоиск без повторного чтения исходного Excel, если RUN ещё существует.

## Architecture boundaries

Business matcher разместить в Business Core/Application Workflow; он не должен зависеть от UI, filesystem paths или openpyxl objects.

Допустимые зоны изменений:

- core models / новый exact matcher;
- references parser and persistence для классификатора;
- application service;
- export adapter;
- home/run templates и минимальный JS;
- targeted tests;
- docs/governance handoff.

Не менять:

- legacy/protected intake semantics;
- ERP hierarchy parser semantics;
- source CFO exact mapping semantics;
- launcher/port cleanup без объективной необходимости;
- ADO/ODBC/1C/live write.

## Acceptance tests

Обязательно добавить тесты:

1. точный ERP-код даёт автоматическое соответствие;
2. точный полный путь работает при отсутствии кода;
3. точное имя разрешено только при уникальности;
4. два кандидата не выбираются автоматически;
5. отсутствующий кандидат остаётся `Требует внимания`;
6. различие регистра не исправляется автоматически;
7. опечатка не исправляется автоматически;
8. одинаковые выходные ключи агрегируются;
9. ноль сохраняется;
10. отрицательная сумма сохраняет знак;
11. листы строго `OPIU Light`, `ОПИУ`, `Показатели`;
12. старый лист `OPIU Light` не меняет схему;
13. ADO-лист `ОПИУ` не регрессирует;
14. `Показатели` содержит точные 8 заголовков;
15. пустые справочные коды не блокируют экспорт;
16. UI не требует ручного Rules workflow;
17. повторный автопоиск после дополнения классификатора не перечитывает Excel;
18. полный regression suite;
19. Windows package smoke.
