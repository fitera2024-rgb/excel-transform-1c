## Вывод

Основная причина несоответствий — системная ошибка разбора иерархического ERP-справочника, а не различия между книгами АЮ и ПВ. Текущий справочник приложения точно воспроизводит результат текущего парсера, однако парсер изменяет путь или имя 249 из 271 ERP-записи. После независимого диагностического восстановления иерархии точный полный путь появляется для 189 из 195 строк АЮ (96,92%) и 179 из 184 строк ПВ (97,28%).

Оставшийся объём — 6 строк АЮ и 5 строк ПВ, или 6 уникальных бизнес-контекстов. Три контекста общие для обеих книг. Для них требуются видимое подтверждение текстового отличия либо явный выбор ERP-кода; fuzzy matching и молчаливое исправление не нужны.

Рекомендация: сначала исправить разбор ERP-иерархии и перечитать справочник, затем обрабатывать остаток через иерархический выбор с сохранением подтверждённого соответствия по полному бизнес-контексту. Строгое точное сопоставление должно остаться основным правилом.

## Факты о текущем ERP-справочнике

- В каталоге приложения 271 запись и 271 уникальный ERP-код; повторных кодов нет.
- Сохранённый payload локального приложения без расхождений совпадает с результатом текущего парсера исходного ERP-файла.
- Текущий парсер меняет имя или путь 249 из 271 записей (91,88%) относительно независимого восстановления иерархии из исходного файла.
- В текущем искажённом представлении 17 повторяющихся значений имени охватывают 217 записей; пять повторных полных путей охватывают 10 записей.
- После восстановления иерархии 37 повторяющихся значений имени охватывают 100 записей; четыре повторных полных пути охватывают восемь записей. Поэтому сопоставление только по имени принципиально неоднозначно.
- В ERP-файле есть девять записей в ветках с маркером `Удалить`/`!!!Удалить`. Ни одна строка АЮ или ПВ не попала в такую ветку. Записи не исключались автоматически.
- В текущей локальной базе manual mappings отсутствуют, поэтому `MANUAL_MAPPING_CONFLICT = 0`. База и mappings не изменялись.
- Во всех 379 исходных строках тип, группа и статья заполнены; `SOURCE_STRUCTURE_PROBLEM = 0`.

## Системные причины

### 1. Техническое значение в строке ERP-кода заменяет официальную статью

В исходном ERP-файле официальный узел статьи обычно расположен строкой выше кода. В строке с кодом колонка наименования может быть пустой либо содержать техническую аналитику, например `Счет затрат 26`. Текущий парсер сначала добавляет непустое значение этой строки в стек иерархии и только затем создаёт ERP-запись. В результате техническая аналитика становится `source_article`, а официальная статья сдвигается в `expense_group`.

Пример: для кода `ЦБ-000239` исходный ERP-файл задаёт путь `Административные расходы → Командировочные → Проживание`, а текущий каталог содержит `Административные расходы → Проживание → Счет затрат 26`.

### 2. Два разных масштаба уровня вложенности интерпретируются как один

Исходный ERP-файл кодирует один уровень иерархии двумя единицами Excel `indent`, а `outlineLevel` — одной единицей. Текущий парсер берёт `max(indent, outlineLevel, leading spaces)` без пересчёта `indent`, из-за чего стек получает завышенную глубину и соседние узлы могут стать родителями друг друга.

Пример: ERP-код `00-000150` должен иметь путь `Расходы на складскую логистику → Содержание оборудования → Содержание ХО установок`, но текущий каталог содержит группу `Содержание ларей`.

### 3. Строгий matcher корректно блокирует искажённый путь

Текущий matcher использует точный полный путь и не должен угадывать. Массовый `REFERENCE_PARSE_PROBLEM` — следствие дефекта входного ERP-представления, а не причина переходить на fuzzy matching.

### 4. Небольшой остаток относится к данным и бизнес-выбору

После диагностического исправления парсера остаются:

- один общий case-only контекст: 2 строки АЮ и 1 строка ПВ;
- два общих контекста без точного ERP-имени: 3 строки АЮ и 2 строки ПВ;
- один неоднозначный name-only контекст только АЮ;
- два неоднозначных name-only контекста только ПВ.

Итого: 11 строк, 6 уникальных контекстов; три контекста общие для книг.

## Гипотезы, требующие проверки при реализации

Следующие утверждения не применялись к данным и остаются прогнозом:

1. После исправления двух правил парсера и повторной загрузки того же ERP-файла 368 строк перейдут из `REFERENCE_PARSE_PROBLEM` в exact-категории.
2. Шесть уникальных остаточных контекстов достаточно подтвердить один раз и затем безопасно переиспользовать по полному ключу, если mapping инвалидируется или помечается вниманием при изменении каталога.
3. Case-only allowlist даст ровно одно уникальное дополнительное соответствие в текущих двух книгах; расширение allowlist без новых данных не оправдано.
4. Формат ERP-экспорта может измениться, поэтому правило масштаба `indent` нельзя считать универсальным без проверки на следующем реальном экспорте.

## Решения владельца

Нужны следующие точные решения:

1. Подтвердить трактовку ERP-экспорта: официальный узел статьи берётся из ближайшей предшествующей иерархической строки, а непустое значение строки с кодом является технической аналитикой и не заменяет статью.
2. Разрешить отдельную implementation-задачу на исправление парсера, regression-тесты и контролируемую повторную загрузку каталога.
3. Решить, должны ли ветки `Удалить` оставаться видимыми для ручного выбора или исключаться только по отдельному явному бизнес-правилу.
4. Для АЮ-контекста `Орг.техника и комплектующие` и двух ПВ-контекстов внереализационной деятельности выбрать правильные ERP-коды либо подтвердить изменение исходной иерархии.
5. Для двух `NO_EXACT_NAME` контекстов подтвердить правильный ERP-код или потребовать исправления исходной статьи; автоматическое исправление текста не разрешать.
6. Одобрить или отклонить case-only allowlist для `Услуги бухгалтера/аудитора`; при одобрении оставить видимый статус и подтверждение.
7. Одобрить сохранение manual mapping только по ключу `тип отчёта → тип расходов → группа расходов → исходная статья` и определить поведение при обновлении ERP-каталога.
