## 1. Цель — ACCEPTED

Создать локальный внутренний сервис для повторяемого преобразования ограниченного набора бюджетных Excel-таблиц в согласованный нормализованный формат для 1С:

`Excel → structural detection → validation → exact business resolution → user corrections → 12-month normalization → preview → three-sheet result`

Главная продуктовая установка: **быстрый рабочий помощник, который сохраняет максимум полезных данных, а не тяжёлый контрольный шлюз**.

## 2. Границы V1 — ACCEPTED

Канонический preview/export scope:

- работает с Excel, встроенными базовыми справочниками и локальными дополнениями;
- структурно обрабатывает подготовленные бюджеты, полный БДР и Инталев ОПИУ;
- сохраняет KPI, доходы и расходы как разные типы показателей;
- валидирует, сопоставляет, нормализует и показывает preview;
- позволяет исправлять бизнес-реквизиты;
- определяет показатели ОПИУ только по принятым exact-правилам;
- экспортирует `OPIU Light / ОПИУ / Показатели`;
- не пишет в 1С/БД.

Не входит:

- ADO live write, TEST/PROD write и прямой SQL-write;
- произвольная реконструкция бюджета из неизвестных расчётных листов;
- универсальная Excel/ERP-платформа, multi-tenant SaaS или enterprise RBAC framework;
- R005, R001, Rules Engine, source-proof UI и обязательные технические SHA/digest controls в normal UI;
- тяжёлое governance/release orchestration без конкретного доказанного риска.

Live write разрешается только отдельным будущим owner gate.

## 3. Официальные входы V1 — ACCEPTED / OWNER EXPANDED

V1 поддерживает три доказанные структурные семьи входов:

1. уже подготовленные загрузочные диапазоны расходов и доходов внутри бюджетного Excel;
2. годовой или одногомесячный отчёт Инталев ОПИУ, из которого структурно извлекаются период, иерархия статей, исходный ЦФО и значения;
3. полный БДР, который структурно обрабатывается как один бизнес-источник и содержит KPI, доходы, расходы и доказанные внутренние prepared-компоненты.

Для подготовленного бюджета сервис не реконструирует строки из расчётных листов департаментов, `полного массива`, исторических листов или внутренних драйверов модели.

Все семьи определяются по обязательным колонкам, периодам и структуре данных, а не по имени файла или листа. Варианты `загрузка в ERP расходы` и `загрузка ERP расходы` распознаются одной схемой. Инталев ОПИУ и полный БДР имеют отдельные structural parser contracts и не подменяются generic 12-month matrix.

Полный БДР не показывается пользователю как набор несвязанных диапазонов. Сервис формирует один RUN и точную RUN-local identity для каждой строки/ячейки, при этом видимый номер Excel-строки остаётся исходным указателем. KPI не зависит от наличия статьи расходов. Доходные и расходные prepared-компоненты входят в тот же результат без поиска «последнего файла» или повторного угадывания источника.

Фактический Excel-контейнер определяется по содержимому. Разрешены обычный OOXML, защищённый OOXML, legacy BIFF/XLS, SpreadsheetML XML и узко восстанавливаемый OOXML. Исходные bytes сохраняются неизменными, обработка использует отдельную RUN-local рабочую копию. Неоднозначный или небезопасно восстанавливаемый файл закрывается понятной ошибкой.

Если найдено несколько структурно подходящих диапазонов, сервис предлагает понятный пользовательский выбор и не угадывает источник молча.

### 3.1. Встроенные базовые справочники — ACCEPTED / OWNER EXPANDED

База, пользовательские дополнения и mappings сохраняются локально после restart.

## 6. Период — ACCEPTED

Интерфейс поддерживает отдельные элементы выбора года и месяца:

- только год — preview/result содержит все 12 месяцев выбранного года;
- год и один/несколько месяцев — интерфейс может показать или экспортировать выбранные месяцы;
- только месяц(ы) — допустимо, если год однозначно задан выбранным сценарием; иначе сервис предлагает указать год.

Внутренняя identity месячной записи всегда содержит:

- календарный год;
- номер месяца `1–12`.

Независимо от экранного фильтра трансформация формирует все 12 месяцев исходной строки, включая нулевые значения. Месячный выбор не должен разрушать полный нормализованный результат.

## 7. Пользовательский организационный контекст — ACCEPTED

`Организации`, юридические лица, промежуточные узлы, подразделения и ЦФО образуют одно вложенное дерево.

Для текущей единицы отчёта `ПС` заранее не закрепляется автоматический mapping на ветку `ПС`, `Б_ПС` или юридическую организацию. Пользователь выбирает нужный узел/ветку вручную при каждом запуске.

Правила:

- `Единица отчёта` и `Организация` остаются разными реквизитами;
- сервис показывает все узлы загруженного дерева без автоматического фильтра по не доказанным полям `Статус` и `Тип узла`;
- для различения показываются доступные код и полный путь;
- названия вроде `!!!Удалить` или `Удалить` не являются основанием для автоматического скрытия или исключения;
- пользователь может выбрать любой доступный узел дерева.

## 10. ERP-сопоставление статей — ACCEPTED

- Конечный идентификатор сопоставления — один определённый ERP-код.
- Название статьи само по себе не является глобальным ключом.
- Автоматический ERP-код разрешён только при точном однозначном соответствии принятой иерархии/атрибутов одному коду.
- Fuzzy matching, автоматическое исправление опечаток, case-insensitive подмена и самостоятельное игнорирование иерархии запрещены.
- Если exact match отсутствует или неоднозначен, пользователь вручную выбирает ERP-код.
- До ручного выбора запись остаётся в preview со статусом `Требует внимания`.

Подтверждённый ручной mapping можно повторно применять при совпадении:

- вида отчёта;
- полного исходного пути `тип расходов → группа расходов → исходная статья`.

Организация, департамент и ЦФО не входят в базовый reusable key. Если возникает реальный конфликт, mapping не применяется молча и снова требует пользовательского выбора.

Фактическое покрытие текущих 179 строк актуальным ERP-справочником:

- 171 точное уникальное соответствие;
- 4 конфликта иерархии;
- 4 отсутствующих точных наименования;
- 0 случаев с несколькими кодами после точного полного пути.

### 10.1. Показатели ОПИУ и точные formula/source rules — ACCEPTED

Для расходов показатель определяется строго по цепочке:

`группа раскрытия → статья внутри группы → поддержанные exact-условия формулы/источника → показатель`.

Правила:

- deepest exact group внутри принятой иерархии имеет приоритет над более общей группой;
- exact ERP-код уточняет кандидата, но конфликтующий код не игнорируется;
- неподдержанное условие MXL/formula fail closed и остаётся `Требует внимания`;
- глобальный поиск только по названию статьи, fuzzy, contains, исправление регистра/опечаток и выбор первого кандидата запрещены;
- загруженный комплект формул/аналитик/MXL является authority для расходов и не может быть молча перекрыт legacy classifier;
- legacy однофайловый classifier остаётся совместимым fallback только для точного `группа → статья`;
- KPI полного БДР сохраняет точный исходный показатель и не требует статьи расходов;
- доходы и количества продолжают использовать свои exact structural resolvers;
- `core/opiu_rules` является узким доменным resolver, а не универсальным Rules Engine и не normal-user rules editor.

## 11. Налогообложение — ACCEPTED на текущем evidence

Допустимые значения в дальнейшем определяются утверждённым справочником, а не постоянным списком в коде.

Для исследованных данных:

- `БЕЗ НДС` — допустимо;
- числовое `0.2` → `20%`;
- числовое `0.22` → `22%`;
- `?`, пустое и числовой `0` требуют внимания;
- числовой `0` нельзя интерпретировать как `0%`, поскольку он мог возникнуть из пустой исходной ячейки;
- явное `0%` допустимо только как однозначное значение утверждённого справочника.

Проблема налогообложения блокирует будущую готовность к write, но не блокирует максимально полный preview.

### 11.1. Явное решение «Налогообложение неважно» — ACCEPTED

Пользователь может явно решить для конкретной исходной строки, что налогообложение не требуется для текущего результата.

- пользовательское значение результата: `Не требуется`;
- решение не подставляет НДС, налоговый код или иной налоговый режим;
- снимается только причина `Налогообложение не определено`;
- остальные проблемы строки сохраняются;
- решение применяется ко всем 12 месяцам исходной строки без полного rerun;
- отдельное массовое действие применяется только после явной галки и считает исходные строки, а не месячные записи;
- уже обработанные строки повторно не предлагаются;
- операция идемпотентна.

### 11.2. Сопоставление ЦФО Инталев — ACCEPTED

Экономист может один раз загрузить локальный классификатор ЦФО Инталев и сопоставить каждый точный исходный ЦФО с конкретным узлом дерева 1С.

- классификатор определяется структурно, не по имени файла;
- source identity использует точный доказанный ключ: код, а при его отсутствии полный путь либо точное наименование;
- target — конкретно выбранная организация, подразделение, ЦФО или другой узел загруженного дерева 1С;
- код и полный путь target доступны пользователю;
- одинаковые display names не объединяются автоматически;
- fuzzy, typo, case-insensitive и name-only guessing запрещены;
- неоднозначность закрывает только конкретное сопоставление и оставляет preview доступным;
- подтверждённый mapping сохраняется локально и повторно применяется в следующих запусках к тому же exact source CFO;
- одно соответствие обновляет все строки и месяцы этого source CFO без полного rerun;
- отдельное массовое действие считает уникальные source CFO, требует явной галки, валидирует весь набор до применения и не делает partial update.

Выбор организации текущего RUN и mapping `ЦФО Инталев → узел 1С` остаются разными бизнес-понятиями.

## 12. Отрицательные суммы — ACCEPTED

Отрицательная сумма:

- сохраняется без изменения знака;
- не пропускается;
- остаётся в основном preview/result;
- получает статус `Требует внимания` и понятный комментарий `Отрицательная сумма`.

Сервис не решает самостоятельно, является ли отрицательное значение ошибкой или допустимым резервом.

## 13. Continue with attention — ACCEPTED

Для `Excel → validation → transformation → preview` нет общего fail-closed.

Пользовательские состояния:

- `ОК` — запись сформирована и обязательные реквизиты разрешены;
- `Требует внимания` — запись сформирована максимально полно, но одно или несколько полей требуют решения;
- `Пропущено` — минимальная единица результата не может быть сформирована, остальная обработка продолжается.

Правила:

- локальная ошибка не блокирует весь файл;
- Excel-ошибка в одной месячной ячейке пропускает только соответствующую месячную запись;
- остальные месяцы той же исходной строки и остальные строки продолжают обрабатываться;
- ошибка/отсутствие общего поля не исключает автоматически все 12 месяцев;
- записи с корректными суммами и проблемным общим полем остаются в основном preview со статусом `Требует внимания`;
- скрытый карантин не создаётся;
- ошибки вне официального загрузочного диапазона V1 не анализируются и не блокируют;
- полная остановка допустима только если файл не открывается/повреждён или не найден ни один распознаваемый диапазон.

Формула продукта:

`Preview = максимально полный результат`

`Реестр ошибок = проблемы + точные указатели`

`ADO-ready = только ОК, отдельный будущий контракт`
