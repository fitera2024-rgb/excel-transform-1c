# Product Contract

Актуальные evidence и карты источников:

- `governance/handoffs/HANDOFF-EXCEL-LOGIC-20260812-001.md`;

## 1. Цель — ACCEPTED

Создать локальный внутренний сервис для повторяемого преобразования ограниченного набора бюджетных Excel-таблиц в согласованный нормализованный формат для 1С:

`Excel → structural detection → validation → ERP mapping → user corrections → 12-month normalization → preview/result`

Главная продуктовая установка: **быстрый рабочий помощник, который сохраняет максимум полезных данных, а не тяжёлый контрольный шлюз**.

## 2. Границы V1 — ACCEPTED

Первая vertical slice:

- работает с Excel и локально загруженными справочниками;
- валидирует, сопоставляет, нормализует и показывает preview;
- позволяет исправлять бизнес-реквизиты;
- экспортирует упрощённый OPIU Light результат;
- не пишет в 1С/БД.

Не входит:

- ADO live write, TEST/PROD write и прямой SQL-write;
- самостоятельное построение загрузочных строк из расчётных листов отделов;
- универсальная Excel/ERP-платформа, multi-tenant SaaS или enterprise RBAC framework;
- R005, R001, Rules Engine, source-proof UI и обязательные технические SHA/digest controls в normal UI;
- тяжёлое governance/release orchestration без конкретного доказанного риска.

Live write разрешается только отдельным будущим owner gate.

## 3. Официальный вход V1 — ACCEPTED

Официальный вход — уже подготовленный загрузочный диапазон расходов внутри бюджетного Excel.

Сервис не реконструирует его из:

- расчётных листов департаментов;
- `полный массив`;
- исторических листов;
- внутренних формул и расчётных драйверов бюджетной модели.

Диапазон определяется по структуре обязательных колонок, двенадцати месяцам и данным, а не по точному имени листа. Варианты `загрузка в ERP расходы` и `загрузка ERP расходы` распознаются одной структурной схемой.

Если найдено несколько структурно подходящих диапазонов, сервис предлагает понятный пользовательский выбор и не угадывает источник молча.

## 4. Вид отчёта V1 — ACCEPTED

Поддерживается один вид отчёта:

- наименование: `Отчет о прибылях и убытках`;
- код: `ОтчетОПрибыляхИУбытках`.

Отдельная запись `ОПИУ` / `ОПИУ` не предлагается как альтернативный вид отчёта V1. В интерфейсе вид отчёта показывается как фиксированный контекст либо единственная опция.

## 5. Сценарии — ACCEPTED

### 5.1. Текущий сценарий

`ПЛАН_2026` и `ПЛАН 2026` считаются одним сценарием.

Канонические реквизиты:

- наименование: `ПЛАН 2026`;
- год: `2026`;
- ERP-код `00010` хранится как дополнительный атрибут, но не является единственным идентификатором;
- основной persisted identity — стабильный локальный идентификатор сценария.

### 5.2. Добавление нового сценария

Пользователь может добавить новый сценарий прямо в сервисе.

Минимальные поля:

- наименование;
- год;
- необязательный комментарий.

Новый сценарий:

- сохраняется постоянно в локальном хранилище;
- доступен в следующих запусках;
- виден всем пользователям локального сервиса;
- получает стабильный локальный идентификатор;
- может не иметь ERP-кода.

Сценарий, которого ещё нет в ERP-справочнике, разрешён для validation, transformation, preview и экспорта. Он показывается с отметкой `Не подтверждён справочником ERP`. Пользователь может позднее создать или поправить его в ERP. До подтверждения такой сценарий не является готовым для будущего write.

## 6. Период — ACCEPTED

Интерфейс поддерживает отдельные элементы выбора года и месяца:

- только год — preview/result содержит все 12 месяцев выбранного года;
- год и один/несколько месяцев — интерфейс может показать или экспортировать выбранные месяцы;
- только месяц(ы) — допустимо, если год однозначно задан выбранным сценарием; иначе сервис предлагает указать год.

Внутренняя identity месячной записи всегда содержит:

- календарный год;
- номер месяца `1–12`.

Независимо от экранного фильтра трансформация формирует все 12 месяцев исходной строки, включая нулевые значения. Месячный выбор не должен разрушать полный нормализованный результат.

## 7. Пользовательский организационный контекст — ACCEPTED

`Организации`, юридические лица, промежуточные узлы, подразделения и ЦФО образуют одно вложенное дерево.

Для текущей единицы отчёта `ПС` заранее не закрепляется автоматический mapping на ветку `ПС`, `Б_ПС` или юридическую организацию. Пользователь выбирает нужный узел/ветку вручную при каждом запуске.

Правила:

- `Единица отчёта` и `Организация` остаются разными реквизитами;
- сервис показывает все узлы загруженного дерева без автоматического фильтра по не доказанным полям `Статус` и `Тип узла`;
- для различения показываются доступные код и полный путь;
- названия вроде `!!!Удалить` или `Удалить` не являются основанием для автоматического скрытия или исключения;
- пользователь может выбрать любой доступный узел дерева.

## 8. Делегирование — ACCEPTED

Делегация разрешена на любой узел дерева: организацию, подразделение, ЦФО или промежуточный узел.

- доступ включает выбранный узел и всё его поддерево любой глубины;
- соседние и вышестоящие ветки автоматически не открываются;
- несколько делегаций одному пользователю объединяются;
- пересекающиеся узлы не дублируются.

Это простая локальная иерархическая фильтрация, а не enterprise RBAC.

## 9. Формулы и месяцы — ACCEPTED

- Формулы в подготовленном диапазоне разрешены.
- Пользователь не обязан делать Paste Values.
- Сервис использует сохранённые рассчитанные значения и не является Excel Calculation Engine.
- Каждая исходная строка нормализуется во все 12 месяцев.
- Нулевые месяцы сохраняются.
- Для исследованного файла: 179 исходных строк → 2 148 потенциальных месячных записей.

## 10. ERP-сопоставление статей — ACCEPTED

- Конечный идентификатор сопоставления — один определённый ERP-код.
- Название статьи само по себе не является глобальным ключом.
- Автоматический ERP-код разрешён только при точном однозначном соответствии принятой иерархии/атрибутов одному коду.
- Fuzzy matching, автоматическое исправление опечаток, case-insensitive подмена и самостоятельное игнорирование иерархии запрещены.
- Если exact match отсутствует или неоднозначен, пользователь вручную выбирает ERP-код.
- До ручного выбора запись остаётся в preview со статусом `Требует внимания`.

Подтверждённый ручной mapping можно повторно применять при совпадении:

- вида отчёта;
- полного исходного пути `тип расходов → группа расходов → исходная статья`.

Организация, департамент и ЦФО не входят в базовый reusable key. Если возникает реальный конфликт, mapping не применяется молча и снова требует пользовательского выбора.

Фактическое покрытие текущих 179 строк актуальным ERP-справочником:

- 171 точное уникальное соответствие;
- 4 конфликта иерархии;
- 4 отсутствующих точных наименования;
- 0 случаев с несколькими кодами после точного полного пути.

## 11. Налогообложение — ACCEPTED на текущем evidence

Допустимые значения в дальнейшем определяются утверждённым справочником, а не постоянным списком в коде.

Для исследованных данных:

- `БЕЗ НДС` — допустимо;
- числовое `0.2` → `20%`;
- числовое `0.22` → `22%`;
- `?`, пустое и числовой `0` требуют внимания;
- числовой `0` нельзя интерпретировать как `0%`, поскольку он мог возникнуть из пустой исходной ячейки;
- явное `0%` допустимо только как однозначное значение утверждённого справочника.

Проблема налогообложения блокирует будущую готовность к write, но не блокирует максимально полный preview.

## 12. Отрицательные суммы — ACCEPTED

Отрицательная сумма:

- сохраняется без изменения знака;
- не пропускается;
- остаётся в основном preview/result;
- получает статус `Требует внимания` и понятный комментарий `Отрицательная сумма`.

Сервис не решает самостоятельно, является ли отрицательное значение ошибкой или допустимым резервом.

## 13. Continue with attention — ACCEPTED

Для `Excel → validation → transformation → preview` нет общего fail-closed.

Пользовательские состояния:

- `ОК` — запись сформирована и обязательные реквизиты разрешены;
- `Требует внимания` — запись сформирована максимально полно, но одно или несколько полей требуют решения;
- `Пропущено` — минимальная единица результата не может быть сформирована, остальная обработка продолжается.

Правила:

- локальная ошибка не блокирует весь файл;
- Excel-ошибка в одной месячной ячейке пропускает только соответствующую месячную запись;
- остальные месяцы той же исходной строки и остальные строки продолжают обрабатываться;
- ошибка/отсутствие общего поля не исключает автоматически все 12 месяцев;
- записи с корректными суммами и проблемным общим полем остаются в основном preview со статусом `Требует внимания`;
- скрытый карантин не создаётся;
- ошибки вне официального загрузочного диапазона V1 не анализируются и не блокируют;
- полная остановка допустима только если файл не открывается/повреждён или не найден ни один распознаваемый диапазон.

Формула продукта:

`Preview = максимально полный результат`

`Реестр ошибок = проблемы + точные указатели`

`ADO-ready = только ОК, отдельный будущий контракт`

## 14. Реестр ошибок — ACCEPTED

Для каждой проблемы сохраняется максимум доступного пользовательского контекста:

- исходный файл;
- лист;
- адрес ячейки;
- номер исходной строки;
- поле / месяц;
- единица отчёта;
- департамент;
- отдел / ЦФО;
- тип расходов;
- группа;
- статья;
- исходное ошибочное значение / тип Excel-ошибки;
- понятное русское описание.

Запись должна позволять быстро найти конкретную проблемную ячейку в исходном Excel.

## 15. Пользовательские исправления — ACCEPTED

Пользователь может прямо в сервисе явно исправлять бизнес-реквизиты из утверждённых справочников, включая:

- налогообложение;
- департамент;
- ЦФО;
- группу;
- статью;
- ERP-код;
- другие поля, для которых есть доказанный справочник.

Исправление является user override, а не тихой подменой. Исходное и выбранное значение можно хранить во внутреннем trace/support layer без тяжёлого технического UX. Preview обновляется без потери уже обработанных данных и без обязательного полного перезапуска.
