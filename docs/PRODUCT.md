## 1. Цель — ACCEPTED

Создать локальный внутренний сервис для повторяемого преобразования ограниченного набора бюджетных Excel-таблиц в согласованный нормализованный формат для 1С:

`Excel → structural detection → validation → ERP mapping → user corrections → 12-month normalization → preview/result`

Главная продуктовая установка: **быстрый рабочий помощник, который сохраняет максимум полезных данных, а не тяжёлый контрольный шлюз**.

## 2. Границы первой версии — ACCEPTED

Первая vertical slice:

- работает с Excel и загруженными справочниками;
- валидирует, сопоставляет, нормализует и показывает preview;
- экспортирует упрощённый OPIU Light результат;
- не пишет в 1С/БД.

Не входит:

- ADO live write, TEST/PROD write и прямой SQL-write;
- самостоятельное построение загрузочных строк из расчётных листов отделов;
- универсальная Excel/ERP-платформа, multi-tenant SaaS или enterprise RBAC framework;
- R005, R001, Rules Engine, source-proof UI и обязательные технические SHA/digest controls в normal UI;
- тяжёлое governance/release orchestration без конкретного доказанного риска.

Реализацию не начинать до явного принятия User Flow владельцем. Live write разрешается только отдельным owner gate.

## 3. Официальный вход V1 — ACCEPTED

Официальный вход — уже подготовленный загрузочный диапазон расходов внутри бюджетного Excel.

Сервис не реконструирует его из:

- расчётных листов департаментов;
- `полный массив`;
- исторических листов;
- внутренних формул и расчётных драйверов бюджетной модели.

Диапазон определяется по структуре обязательных колонок, двенадцати месяцам и данным, а не по точному имени листа. Варианты `загрузка в ERP расходы` и `загрузка ERP расходы` должны распознаваться одной структурной схемой.

Если найдено несколько структурно подходящих диапазонов, сервис не угадывает, а предлагает пользователю понятный выбор.

## 4. Пользовательский контекст — ACCEPTED

До обработки Excel пользователь выбирает значения из актуальных загруженных справочников:

- единицу отчёта;
- организацию/узел пути 1С;
- сценарий;
- период сценария / год;
- вид отчёта;
- при необходимости другие доказанно необходимые связанные реквизиты.

Правила:

- значения не hardcode-ятся;
- не определяются по имени файла, каталогу или случайной ячейке workbook;
- `Единица отчёта` и `Организация` остаются разными реквизитами;
- `Сценарий` и `Период сценария` остаются разными реквизитами;
- если Excel содержит явное противоречие выбранному контексту, сервис показывает понятную проблему;
- если реквизит нельзя надёжно подтвердить по Excel, authority остаётся пользовательский выбор.

Для текущего примера ранее подтверждено значение сценария `ПЛАН_2026`, но оно не является hardcode. Актуальный экспорт сценариев содержит `ПЛАН 2026`, код `00010`; это OPEN-расхождение и не должно исправляться автоматически.

## 5. Формулы и месяцы — ACCEPTED

- Формулы в подготовленном диапазоне разрешены.
- Пользователь не обязан делать Paste Values.
- Сервис использует сохранённые рассчитанные значения и не является Excel Calculation Engine.
- Каждая исходная строка нормализуется во все 12 месяцев.
- Нулевые месяцы сохраняются.
- Для исследованного файла: 179 исходных строк → 2 148 потенциальных месячных записей.

## 6. ERP-сопоставление статей — ACCEPTED

- Конечный идентификатор сопоставления — один определённый ERP-код.
- Название статьи само по себе не является глобальным ключом.
- Автоматический ERP-код разрешён только при точном однозначном соответствии принятой иерархии/атрибутов одному коду.
- Fuzzy matching, автоматическое исправление опечаток, case-insensitive подмена и самостоятельное игнорирование иерархии запрещены.
- Если exact match отсутствует или неоднозначен, пользователь вручную выбирает ERP-код.
- До ручного выбора запись остаётся в preview со статусом `Требует внимания` и не считается будущей ADO-ready.
- Подтверждённое вручную соответствие можно повторно применять только в доказанно том же контексте; точный context key остаётся OPEN.

Фактическое покрытие текущих 179 строк актуальным ERP-справочником:

- 171 точное уникальное соответствие;
- 4 конфликта иерархии;
- 4 отсутствующих точных наименования;
- 0 случаев с несколькими кодами после точного полного пути.

## 7. Налогообложение — ACCEPTED на текущем evidence

Допустимые значения в дальнейшем определяются утверждённым справочником, а не постоянным списком в коде.

Для исследованных данных:

- `БЕЗ НДС` — допустимо;
- числовое `0.2` → `20%`;
- числовое `0.22` → `22%`;
- `?`, пустое и числовой `0` требуют внимания;
- числовой `0` нельзя интерпретировать как `0%`, поскольку он мог возникнуть из пустой исходной ячейки;
- явное `0%` допустимо только как однозначное значение утверждённого справочника.

Проблема налогообложения блокирует будущую готовность к write, но не блокирует максимально полный preview.

## 8. Continue with attention — ACCEPTED

Для `Excel → validation → transformation → preview` нет общего fail-closed.

Пользовательские состояния:

- `ОК` — запись сформирована и обязательные реквизиты разрешены;
- `Требует внимания` — запись сформирована максимально полно, но одно или несколько полей требуют решения;
- `Пропущено` — минимальная единица результата не может быть сформирована, остальная обработка продолжается.

Правила:

- локальная ошибка не блокирует весь файл;
- Excel-ошибка в одной месячной ячейке пропускает только соответствующую месячную запись;
- остальные месяцы той же исходной строки и остальные строки продолжают обрабатываться;
- ошибка/отсутствие общего поля не исключает автоматически все 12 месяцев;
- записи с корректными суммами и проблемным общим полем остаются в основном preview со статусом `Требует внимания`;
- скрытый карантин не создаётся;
- ошибки вне официального загрузочного диапазона V1 не анализируются и не блокируют;
- полная остановка допустима только если файл не открывается/повреждён или не найден ни один распознаваемый диапазон.

Формула продукта:

`Preview = максимально полный результат`

`Реестр ошибок = проблемы + точные указатели`

`ADO-ready = только ОК, отдельный будущий контракт`

## 11. Организации, ЦФО и доступ — ACCEPTED

`Организации`, юридические лица, промежуточные узлы, подразделения и ЦФО образуют один вложенный справочник, а не независимые списки.

- Делегация на организацию распространяется на всё её поддерево любой глубины.
- Соседние и вышестоящие ветки автоматически не открываются.
- Пользователю можно делегировать несколько организаций.
- Effective access — объединение всех делегированных поддеревьев.
- Экранные списки организационного контекста ограничиваются этой областью.

Это простая иерархическая фильтрация локального сервиса; enterprise RBAC не требуется.
