# Product Contract

STATUS: `DRAFT / OWNER_INPUT_REQUIRED`

Полный discovery/evidence handoff: `governance/handoffs/HANDOFF-COORDINATOR-20260811-001.md`.

## Цель

Создать лёгкий внутренний сервис для цепочки:

`Excel → validation → transformation → preview → later ADO DRY RUN → controlled 1C write`.

Главная продуктовая установка: **быстрый рабочий помощник, а не контрольный шлюз**.

## Жёсткие границы старта

- OPIU используется только как визуальный/UX reference и источник отдельных reliability/safety patterns.
- Не копировать R005, R001, Rules Engine и source-proof UI.
- Первая vertical slice не пишет в 1С/БД.
- Live write по умолчанию запрещён.
- Production — отдельный owner gate.
- Реализацию не начинать до принятия User Flow владельцем.

## Источник первой версии — ACCEPTED

Официальный вход первой версии — уже подготовленный загрузочный диапазон Excel.

- Не реконструировать его из расчётных департаментских листов, `полный массив`, historical sheets или внутренних budget-formulas.
- Определять загрузочный диапазон по структуре обязательных колонок/данным, а не по точному имени sheet.
- Формулы в диапазоне разрешены; пользователь не обязан делать Paste Values.
- Сервис использует рассчитанное/сохранённое значение и не является Excel Calculation Engine.

## Нормализация месяцев — ACCEPTED

Каждая исходная загрузочная строка формирует все 12 месяцев, включая нулевые.

Нулевые месяцы не удаляются как «лишние».

## ERP-сопоставление — ACCEPTED

- Имя статьи само по себе не является глобальным ключом.
- Автоматически использовать ERP-код можно только при точном однозначном match по принятой иерархии/атрибутам.
- При неоднозначности пользователь выбирает ERP-код вручную.
- Не использовать autonomous fuzzy matching, auto typo correction или самостоятельный выбор кода.
- Неразрешённый mapping остаётся видимым в preview как `Требует внимания`; будущий ADO-ready определяется отдельно.

## Контекст и справочники — ACCEPTED

Контекст задаёт пользователь в UI из загруженных утверждённых справочников.

Ожидаемые группы справочников:

- единицы отчёта;
- организации пути 1С;
- сценарии;
- периоды сценария;
- виды отчётов;
- ЦФО / подразделения;
- налогообложение;
- другие реально необходимые связанные справочники.

Не hardcode-ить значения и не определять их по filename/path/случайной ячейке workbook.

`Единица отчёта` и `Организация пути 1С` — разные поля до доказанного mapping.

`Сценарий` и `Период сценария` — разные поля.

Наблюдавшиеся `ПС`, `АЮ`, `Владивосток`, `ПЛАН_2026` — примеры, не единственно допустимые значения.

## Пользовательское исправление реквизитов — ACCEPTED

Пользователь может исправлять бизнес-реквизиты прямо в сервисе из загруженных справочников, включая:

- налогообложение;
- департамент;
- ЦФО;
- группу;
- статью;
- ERP-код;
- другие поля с утверждённым справочником.

Правка является явным user override, а не тихой автоматической подменой. Исходное и выбранное значение можно сохранять во внутреннем trace/audit без тяжёлого технического UX.

## Принцип обработки ошибок — ACCEPTED

Основной принцип первой версии: **обработать максимум корректных данных и собрать проблемы в понятный Реестр ошибок, не останавливая весь процесс без технической необходимости**.

Пользовательские состояния:

- `ОК` — значение/строка обработаны;
- `Требует внимания` — результат сформирован настолько, насколько возможно, проблема зарегистрирована;
- `Пропущено` — конкретное значение или минимально необходимая единица данных не может быть сформирована, но остальная обработка продолжается.

Правила:

- ошибка в одной ячейке, статье, ERP-сопоставлении, налогообложении или строке не останавливает весь файл;
- пропускается только минимально необходимая проблемная единица данных;
- по проблеме создаётся запись в Реестре ошибок с точным указателем на исходный Excel;
- частичный полезный результат является допустимым результатом первой версии;
- полная остановка допускается только когда обработку технически невозможно продолжать вообще, например файл невозможно открыть, файл повреждён или не найден ни один распознаваемый загрузочный диапазон;
- более строгие ограничения для фактической записи в 1С определяются отдельно на этапе ADO/live-write.

### Ошибка в общем поле строки — ACCEPTED

Ошибка в общем поле исходной строки (`статья`, `группа`, `департамент`, `ЦФО`, `налогообложение` и т. п.) **не является основанием автоматически исключать все 12 месяцев этой строки**.

Принцип: **переносить всё, что можно перенести корректно; не переносить только то, что действительно невозможно сформировать из-за конкретной ошибки**.

Корректные месячные суммы и остальные корректные поля сохраняются. Проблемное поле может остаться неразрешённым, запись получает `Требует внимания`, а проблема попадает в Реестр ошибок.

### Ошибка формулы/ячейки — ACCEPTED

Если рассчитанное значение отдельной ячейки даёт `#REF!`, `#N/A`, `#DIV/0!` или другую непригодную ошибку:

- не блокировать весь файл;
- не удалять автоматически всю исходную строку;
- пропустить только минимально необходимый результат, который нельзя корректно сформировать;
- остальные корректные месяцы/данные продолжить;
- добавить точную запись в Реестр ошибок.

Ошибки вне официально обрабатываемого загрузочного диапазона первую версию не блокируют.

### Видимость неполных записей в Preview — ACCEPTED

Основной нормализованный preview/result показывает **максимально полный результат**, включая записи с локально неразрешёнными реквизитами.

Такие записи остаются в основном preview/result со статусом `Требует внимания`; отдельный скрытый карантин не создаётся.

Принцип:

`Preview = максимально полный результат`

`Реестр ошибок = проблемы и точные указатели`

`ADO-ready = отдельный будущий фильтр готовности к записи`

## Налогообложение — ACCEPTED на текущем evidence

В исследованном наборе распознавались:

- `БЕЗ НДС`;
- `0.2` → 20%;
- `0.22` → 22%.

`?`, пустое и неоднозначный числовой `0` требуют внимания.

Числовой `0` нельзя автоматически трактовать как 0%, поскольку в исследованном Excel он мог происходить из пустого источника.

Эти проблемы не блокируют файл: запись остаётся максимально полной и может быть исправлена пользователем из справочника.

## Реестр ошибок / внимания — ACCEPTED концепция

Запись должна содержать максимум доступного пользовательского контекста и точный указатель на источник, например:

- файл;
- sheet;
- cell address;
- номер исходной строки;
- поле / месяц;
- единица отчёта;
- департамент;
- ЦФО;
- тип/группа/статья;
- исходное проблемное значение;
- понятное русское описание.

Не требовать все поля, если часть контекста из-за ошибки недоступна.

## Пользовательский результат первой версии — ACCEPTED направление

Не копировать технический 34-column sample-result как обязательный user format.

Пользовательский normalized result должен содержать бизнес-поля: единица отчёта, сценарий, год/месяц/период, департамент, вид организации, отдел/ЦФО, тип расходов, группа, исходная статья, ERP-код, официальная ERP-статья, налогообложение, сумма, status, comment/reason, source row.

Technical SHA, BatchID, internal keys, paths и technical blocker codes остаются внутренними при необходимости.
