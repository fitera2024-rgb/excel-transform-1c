## 1. Текущий проект User Flow

### Шаг 1. Доступные справочники

Сервис использует загруженные утверждённые справочники. Значения не зашиваются в код и не угадываются по имени файла.

Для организационного контекста используется единое вложенное дерево `Организации`, содержащее организации, промежуточные узлы, подразделения и ЦФО.

### Шаг 2. Область доступа пользователя

Для пользователя формируется effective access:

- каждая делегированная организация открывает всё своё поддерево любой глубины;
- при нескольких делегациях доступ равен объединению поддеревьев;
- соседние и вышестоящие ветки не открываются автоматически;
- пересекающиеся узлы не дублируются.

Экран выбора организационного контекста показывает только разрешённые узлы.

### Шаг 3. Выбор контекста до Excel

Пользователь выбирает отдельные реквизиты:

- единицу отчёта;
- организацию/узел пути 1С из разрешённого дерева;
- сценарий;
- период сценария / год;
- вид отчёта;
- другие доказанно необходимые связанные значения.

Не объединять автоматически:

- единицу отчёта и организацию;
- сценарий и период сценария.

### Шаг 4. Выбор бюджетного Excel

Пользователь выбирает исходный бюджетный Excel.

Сервис не определяет контекст по filename, folder path или первой найденной ячейке workbook.

### Шаг 5. Структурное обнаружение входа

Сервис ищет подготовленный загрузочный диапазон по обязательным колонкам, двенадцати месяцам и структуре данных.

Точное имя листа не является authority. Варианты `загрузка в ERP расходы` и `загрузка ERP расходы` должны распознаваться одной схемой.

Если найдено несколько подходящих диапазонов, сервис предлагает понятный выбор пользователя и не выбирает источник молча.

Если не найден ни один распознаваемый диапазон, обработка останавливается с понятным действием перевыбора файла/источника.

### Шаг 6. Чтение значений

Формулы разрешены. Сервис читает сохранённые рассчитанные значения Excel и не воспроизводит Excel Calculation Engine.

Ошибки вне выбранного официального диапазона игнорируются V1.

### Шаг 7. Validation и разворот месяцев

Каждая исходная строка разворачивается во все 12 месяцев, включая нулевые.

- корректная месячная ячейка формирует запись результата;
- Excel-ошибка конкретного месяца пропускает только эту минимальную запись;
- ошибка общего поля не удаляет остальные месяцы;
- локальные проблемы регистрируются, но максимально возможная обработка продолжается.

### Шаг 8. Точное ERP-сопоставление

Сервис автоматически назначает ERP-код только при точном однозначном match по принятой иерархии/атрибутам.

Не допускаются:

- fuzzy auto-match;
- автоматическое исправление опечатки;
- самостоятельное игнорирование иерархии;
- глобальный key только по названию статьи.

### Шаг 9. Максимально полный preview

Пользователь видит основной нормализованный preview со статусами:

- `ОК`;
- `Требует внимания`;
- `Пропущено`.

Записи с корректными суммами и неразрешённым общим реквизитом остаются в preview. Отдельный скрытый карантин не создаётся.

### Шаг 10. Реестр ошибок / внимания

Пользователь видит отдельный реестр с точным указателем на исходный Excel:

- файл;
- лист;
- адрес ячейки;
- исходная строка;
- поле / месяц;
- доступный бизнес-контекст;
- исходное значение / тип ошибки;
- понятное русское описание.

### Шаг 11. Явные пользовательские исправления

Пользователь может из утверждённых справочников:

- выбрать ERP-код вручную;
- исправить налогообложение;
- исправить департамент;
- исправить ЦФО;
- исправить группу;
- исправить статью;
- исправить другие доказанно справочные бизнес-реквизиты.

User override не является тихой подменой. Исходное и выбранное значение сохраняются во внутреннем trace/support layer.

### Шаг 12. Обновление результата

После исправления preview и Реестр ошибок обновляются без потери уже обработанных корректных данных и без обязательного полного перезапуска процесса.

### Шаг 13. Экспорт V1

Пользователь экспортирует нормализованный OPIU Light Excel/result с бизнес-полями Product Contract.

Первая vertical slice на этом заканчивается. ADO/write не вызывается.

## 2. UX-инварианты

`Preview = максимально полный результат`

`Реестр ошибок = проблемы + точные указатели`

`ADO-ready = только ОК, отдельный будущий контракт`

Для preview применяется **continue with attention**, а не общий fail-closed.

Полная остановка разрешена только если:

- файл невозможно открыть или он повреждён;
- не найден ни один распознаваемый загрузочный диапазон;
- технически невозможно получить какой-либо полезный результат.

Blocked screen должен содержать понятное действие перевыбора/сброса.

Normal UI использует бизнес-понятия. SHA, internal paths, proof JSON, SQL IDs и technical blocker codes не являются обязательными пользовательскими элементами.

## 3. Не входит в первую vertical slice

- ADO live write;
- TEST/PROD write;
- прямой SQL-write;
- реконструкция подготовленного диапазона из расчётных листов отделов;
- автоматический merge/release;
- тяжёлый source-proof/governance UX;
- универсальный Rules/Plugin Engine;
- самостоятельная очистка/исправление исходного Excel сервисом.

## 4. Визуальный reference

Из OPIU можно использовать:

- знакомую верхнюю навигацию;
- карточки состояния;
- работу с файлами;
- иерархический выбор статей/организаций;
- понятный журнал и OPIU Light layout.

Не копировать тяжёлую внутреннюю архитектуру, многоходовые блокировки и технический proof-UX.
