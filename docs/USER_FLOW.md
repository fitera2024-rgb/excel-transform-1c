## 1. Принятый User Flow V1

### Шаг 1. Доступные справочники

После чистой установки сервис уже содержит базовые ERP-статьи, организации/узлы, сценарии и ЦФО Инталев. Пользователь может сразу перейти к обработке файла.

Действие `Загрузить / дополнить` сохраняется: новые записи добавляются, а существующая запись обновляется только по exact stable key. Базовые записи, пользовательские дополнения и mappings сохраняются в локальной базе после restart; похожие названия не объединяются автоматически.

Для организационного контекста используется единое вложенное дерево `Организации`, содержащее юридические организации, промежуточные узлы, подразделения и ЦФО.

Узлы с названиями вроде `!!!Удалить` или `Удалить` не скрываются и не исключаются автоматически, пока нет доказанного признака активности.

### Шаг 2. Общий доступ к организационному дереву

Владелец снял отдельный блок области доступа и локальные ограничения прав для V1.

- всем пользователям локального сервиса доступно всё загруженное дерево организаций и узлов;
- экран делегирования отсутствует;
- effective-access фильтрация не применяется;
- enterprise RBAC и отдельная модель прав не входят в scope локального конвертера.

### Шаг 3. Иерархический выбор организации

Пользователь выбирает организацию/узел пути 1С вручную при каждом запуске.

Выбор двухэтапный:

1. выбрать верхнюю ветку дерева;
2. оставить выбранным сам верхний узел либо выбрать любую доступную дочернюю организацию, подразделение или ЦФО.

После выбора верхней ветки интерфейс показывает всё её поддерево. Для единицы отчёта `ПС` сервис не устанавливает заранее mapping на ветку `ПС`, `Б_ПС` или юридическую организацию.

Все узлы загруженного дерева показываются без автоматического фильтра по недоказанным полям `Статус` и `Тип узла`. Для различения доступны код, наименование, иерархия и полный путь.

### Шаг 4. Выбор или добавление сценария

Пользователь выбирает существующий сценарий либо добавляет новый.

Для текущего примера:

- `ПЛАН_2026` и `ПЛАН 2026` считаются одним сценарием;
- каноническое имя: `ПЛАН 2026`;
- год: `2026`;
- ERP-код `00010` — дополнительный реквизит, не единственный ключ.

Новый сценарий содержит:

- наименование;
- год;
- необязательный комментарий.

Он сохраняется постоянно локально, виден всем пользователям локального сервиса и получает стабильный локальный идентификатор.

Если сценария нет в ERP-справочнике, пользователь всё равно может продолжить validation, transformation, preview и экспорт. Интерфейс показывает отметку `Не подтверждён справочником ERP`. Пользователь может позднее поправить или создать сценарий в ERP. Будущий write для такого сценария не разрешён до подтверждения.

### Шаг 5. Выбор периода

Интерфейс содержит:

- поле года;
- явную галочку `Весь год`, включённую по умолчанию;
- месяцы `1–12`, доступные после снятия галочки `Весь год`.

Допустимо:

- оставить `Весь год` — получить все 12 месяцев выбранного года;
- снять `Весь год` и выбрать один/несколько месяцев — отфильтровать просмотр/экспорт;
- выбрать месяцы без отдельного года, если год однозначно задан выбранным сценарием.

Если `Весь год` снят, но ни один месяц не выбран, сервис показывает понятное сообщение и не начинает обработку.

Внутренняя identity месячной записи всегда содержит календарный год и номер месяца. Трансформация независимо от фильтра создаёт все 12 месяцев, включая нулевые.

### Шаг 6. Фиксированный вид отчёта

В V1 используется:

- `Отчет о прибылях и убытках`;
- код `ОтчетОПрибыляхИУбытках`.

Интерфейс показывает его как фиксированный контекст либо единственную опцию и не предлагает отдельную запись `ОПИУ`.

### Шаг 7. Выбор исходного Excel

Пользователь выбирает один бизнес-файл из принятых структурных семей:

- подготовленный бюджетный Excel с расходами и/или доходами;
- полный БДР с KPI, доходами и расходами;
- годовой либо одногомесячный отчёт Инталев ОПИУ.

Допустимы `.xlsx`, `.xlsm` и `.xls`; реальный формат определяется по содержимому, а не по расширению.

Для защищённого OOXML пароль вводится только в поле текущей формы и не сохраняется. Старый BIFF/XLS, SpreadsheetML XML и узко восстанавливаемый OOXML преобразуются в отдельную локальную рабочую `.xlsx`-копию. Исходный файл не изменяется.

Сервис не определяет контекст по filename, folder path или случайной ячейке workbook.

### Шаг 8. Структурное обнаружение входа

Сервис ищет одну из трёх принятых схем:

- подготовленные загрузочные диапазоны расходов и доходов по обязательным колонкам, периодам и структуре данных;
- годовой или одногомесячный Инталев ОПИУ по периоду, месячным колонкам, иерархии статей и источнику ЦФО;
- полный БДР как один бизнес-источник, объединяющий KPI, доходные и расходные компоненты с точной source identity.

Точное имя листа не является authority. Варианты `загрузка в ERP расходы` и `загрузка ERP расходы` распознаются одной схемой; Инталев ОПИУ и полный БДР обрабатываются отдельными structural parser contracts.

Если полный БДР распознан, пользователь выбирает один кандидат БДР, а не отдельные внутренние листы. Downstream получает exact RUN-local handoff всех его компонентов и не ищет `latest file`.

Если найдено несколько подходящих диапазонов, сервис предлагает понятный выбор пользователя и не выбирает источник молча.

Если файл нельзя безопасно открыть/восстановить либо не найден ни один распознаваемый диапазон, обработка останавливается с понятным действием перевыбора файла/источника.

### Шаг 9. Чтение значений

Формулы разрешены. Сервис читает сохранённые рассчитанные значения Excel и не воспроизводит Excel Calculation Engine.

Для полного БДР значение показателя за месяц может быть взято из отдельного saved-value sheet только по доказанной точной связи `лист + строка + показатель + месяц`. Текст формулы не подставляется вместо числового значения.

Ошибки вне выбранного официального диапазона игнорируются V1.

### Шаг 10. Validation и разворот месяцев

Подготовленная строка бюджета и годовой источник разворачиваются во все 12 месяцев, включая нулевые. Одногомесячный Инталев сохраняет только доказанный месяц. Полный БДР формирует точные месячные записи для KPI, доходов и расходов без требования статьи расходов для KPI.

- корректная месячная ячейка формирует запись результата;
- Excel-ошибка конкретного месяца пропускает только эту минимальную запись;
- ошибка общего поля не удаляет остальные месяцы;
- локальные проблемы регистрируются, но максимально возможная обработка продолжается;
- отрицательная сумма сохраняется без изменения знака и получает `Требует внимания` с комментарием `Отрицательная сумма`.

### Шаг 11. Точное ERP-сопоставление

Сервис автоматически назначает ERP-код только при точном однозначном match по принятой иерархии/атрибутам.

Не допускаются:

- fuzzy auto-match;
- автоматическое исправление опечатки;
- самостоятельное игнорирование иерархии;
- глобальный key только по названию статьи.

Если match отсутствует или неоднозначен, пользователь выбирает ERP-код вручную.

Подтверждённый ручной mapping может повторно применяться при совпадении:

- вида отчёта;
- полного пути `тип расходов → группа расходов → исходная статья`.

Если обнаружен конфликт, mapping не применяется молча.

### Шаг 11.1. Точное определение показателя ОПИУ

Для расходных строк сервис определяет показатель только по цепочке:

`группа раскрытия → статья внутри группы → поддержанные exact-условия формулы/источника → показатель`.

- загруженный комплект формул/аналитик/MXL является authority для расходов;
- конфликтующий legacy classifier не перекрывает его молча;
- legacy classifier допускается только как exact fallback `группа → статья`, когда formula/source authority отсутствует;
- неподдержанное условие или неоднозначность остаются `Требует внимания`;
- global article-name-only, fuzzy, contains, typo и case-only matching запрещены;
- KPI полного БДР использует точный исходный показатель и не проходит через расходную статью;
- доходы и количества используют свои принятые exact structural resolvers.

Normal user загружает бизнес-источники и видит результат/причину внимания. Технического Rules Engine и обязательного редактора правил в UI нет.

### Шаг 12. Максимально полный preview

Пользователь видит основной нормализованный preview со статусами:

- `ОК`;
- `Требует внимания`;
- `Пропущено`.

Записи с корректными суммами и неразрешённым общим реквизитом остаются в preview. Отдельный скрытый карантин не создаётся.

### Шаг 13. Реестр ошибок / внимания

Пользователь видит отдельный реестр с точным указателем на исходный Excel:

- файл;
- лист;
- адрес ячейки;
- исходная строка;
- поле / месяц;
- доступный бизнес-контекст;
- исходное значение / тип ошибки;
- понятное русское описание.

### Шаг 14. Явные пользовательские исправления

Пользователь может из загруженных справочников:

- выбрать ERP-код вручную;
- исправить налогообложение;
- исправить департамент;
- исправить ЦФО;
- исправить группу;
- исправить статью;
- исправить другие доказанно справочные бизнес-реквизиты.

User override не является тихой подменой. Исходное и выбранное значение сохраняются во внутреннем trace/support layer.

#### Шаг 14.1. Налогообложение не требуется

Для строки с причиной `Налогообложение не определено` пользователь может явно выбрать `Налогообложение неважно`. После применения сервис показывает `Налогообложение: не требуется`, обновляет все месяцы исходной строки без rerun и сохраняет остальные причины.

Отдельный page-level блок позволяет применить это решение ко всем подходящим исходным строкам. Он считает строки один раз, требует явной галки `Подтверждаю для всех строк: налогообложение неважно` и не подставляет налоговый режим.

#### Шаг 14.2. Сопоставление ЦФО Инталев

Экономист загружает классификатор ЦФО Инталев один раз. Для каждого уникального exact source CFO сервис показывает код, наименование/путь, количество исходных строк и иерархический выбор конкретного узла 1С.

Пользователь может:

- подтвердить одно соответствие;
- заполнить несколько соответствий и выбрать `Подтверждаю все заполненные сопоставления ЦФО` → `Применить всё`.

Подтверждённый mapping сохраняется локально, применяется ко всем строкам и месяцам source CFO, сохраняет другие причины и не запускает полную трансформацию повторно. Уже подтверждённые mappings показываются статусом, а не повторной пустой галкой.

### Шаг 15. Обновление результата

После исправления preview и Реестр ошибок обновляются без потери уже обработанных корректных данных и без обязательного полного перезапуска процесса.

### Шаг 16. Экспорт V1

Пользователь экспортирует один XLSX с тремя бизнес-листами:

1. `OPIU Light` — максимально полный нормализованный построчный результат;
2. `ОПИУ` — сохранённый построчный слой для принятого отчёта;
3. `Показатели` — точная агрегация показателей по принятым resolvers.

`OPIU Light` и `ОПИУ` не теряют строки из-за отсутствующего показателя. Неразрешённые formula/source случаи остаются видимыми, а `Показатели` не заполняется догадкой.

Preview/export vertical slice на этом заканчивается. ADO/write не вызывается.

## 2. UX-инварианты

`Preview = максимально полный результат`

`Реестр ошибок = проблемы + точные указатели`

`ADO-ready = только ОК, отдельный будущий контракт`

Для preview применяется **continue with attention**, а не общий fail-closed.

Полная остановка разрешена только если:

- файл невозможно открыть или он повреждён;
- не найден ни один распознаваемый загрузочный диапазон;
- технически невозможно получить какой-либо полезный результат.

Blocked screen содержит понятное действие перевыбора/сброса.

Normal UI использует бизнес-понятия. SHA, internal paths, proof JSON, SQL IDs и technical blocker codes не являются обязательными пользовательскими элементами.

## 3. Не входит в первую vertical slice

- ADO live write;
- TEST/PROD write;
- прямой SQL-write;
- произвольная реконструкция неизвестной бюджетной модели из расчётных листов;
- автоматический merge/release;
- тяжёлый source-proof/governance UX;
- универсальный Rules/Plugin Engine и normal-user технический редактор правил;
- самостоятельная очистка/исправление исходного Excel сервисом;
- автоматическое создание или изменение сценариев непосредственно в ERP;
- отдельный экран прав, делегирование и effective-access фильтрация.

## 4. Визуальный reference

Из OPIU можно использовать:

- знакомую верхнюю навигацию;
- карточки состояния;
- работу с файлами;
- иерархический выбор статей/организаций;
- понятный журнал и OPIU Light layout.

Не копировать тяжёлую внутреннюю архитектуру, многоходовые блокировки и технический proof-UX.
